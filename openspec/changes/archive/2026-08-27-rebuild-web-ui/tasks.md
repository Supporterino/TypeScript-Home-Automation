Task groups follow the six phases in design.md — D1.

| Group | Phase | Depends on |
|---|---|---|
| 1 Asset delivery, failure isolation, dev workflow | ① | — |
| 2 State persistence write-behind and reserved namespace | ② | — |
| 3 Automation control plane | ② | 2 |
| 4 Device capability vocabulary | ② | — |
| 5 Realtime event stream | ③ | 2, 3 |

| 11 Documentation and release | — | 1–10 |

Groups 1, 2, and 4 have no prerequisites and may proceed in parallel. Group 3
follows group 2 (design.md R18): persisting an automation's enabled flag writes
through the reserved namespace defined in 2.9–2.10, and the assertion that the
flag cannot be changed by a raw state write needs stop and start to exist, so it
closes group 3 as task 3.11 rather than sitting in group 2.

Frontend behaviour is verified by hand, not by automated test — there is no DOM
harness and none is added (design.md D23). Every task below that could have
asserted on rendered output instead either asserts on a pure module, or says
"verify manually" and means it. Where a task names a pure module, that module is
the deliverable: logic that ends up inside a component is unreachable by test,
not merely untested.

The stream's device event categories are **not** in group 5. They depend on
qualified device identifiers and observation freshness, which group 6 defines, so
they sit in group 7 alongside the command endpoints (design.md D1). Group 5 ships
the stream carrying state, log, automation, and readiness categories, which is
sufficient to replace the poll for everything except devices.

Task 1.0 (failure isolation) should land before any other group merges. It is
independent of everything and caps the blast radius of the device-shape change in
group 6 and the rebuild in group 10 (design.md R13).

Run `bun run typecheck && bun run check && bun test` before considering any
group complete.

`LogBuffer` is `write()` plus `query()` and nothing else, so 5.0 is a prerequisite
for 5.1's log category rather than an implementation detail of it. Tasks 5.0a–5.0c
close the feedback cycle that adding the subscription opens (design.md D32, R21);
5.0b and 5.0c are both required and neither substitutes for the other.

- [x] 5.0 Add a releasable subscription to `LogBuffer` alongside `write()` and `query()`, notifying registered listeners of each newly stored entry, with a throwing listener neither preventing storage, nor preventing other listeners from being notified, nor propagating to the caller that logged; verify tests cover delivery to a subscriber, release stopping delivery and retaining no reference, and a throwing listener leaving storage and the other listeners unaffected
- [x] 5.0a Defer notification past the write call so listeners are invoked on a later turn of the event loop, keeping fan-out — including network writes to every connected client — off pino's synchronous sink, which every `logger.*` call in the engine reaches (design.md D32, R9); verify a test asserts `write()` returns before any listener is invoked, and benchmark logging throughput with and without the subscription, treating a measurable regression as a blocker on the same terms as 8.9
